# Project Management — тестовое задание (Sibers)

Приложение для работы с проектами: проекты, сотрудники, задачи, документы и права доступа.
Сделано основное задание и оба дополнительных.

## Что использовал

Backend — ASP.NET Core Web API на .NET 8, база SQLite, Entity Framework Core (Code First
с миграциями), вход через ASP.NET Core Identity и JWT-токен.

Frontend — Vue 3 с Vite.

## Как запустить

Нужны .NET 8 SDK и Node.js 18+.

**Backend:**

```bash
dotnet restore
dotnet run --project src/ProjectManagement.Api
```

Запустится на `http://localhost:5000`, Swagger — `http://localhost:5000/swagger`.
База создаётся сама при первом запуске: миграции применяются автоматически, руками ничего
делать не надо. Файл базы — `src/ProjectManagement.Api/projectmanagement.db`, если удалить его,
всё создастся заново.

**Frontend** (в отдельном терминале):

```bash
cd client
npm install
npm run dev
```

Откроется на `http://localhost:5173`. Запросы к `/api` и `/uploads` Vite сам перенаправляет
на backend — это настроено в `client/vite.config.js`.

**Вход в систему.** При первом запуске создаётся руководитель:

- Email: `director@sibers.local`
- Пароль: `Director123!`

Под ним можно завести остальных сотрудников — страница «Сотрудники» видна только руководителю.

## Тесты

```bash
dotnet test
```

30 тестов на слой логики: права всех трёх ролей, проверки при создании проекта (даты,
несуществующий руководитель или исполнители), фильтры и сортировки, правила назначения
исполнителя и смены статуса задачи. Тесты работают на SQLite в памяти — отдельная база
для каждого теста, ничего настраивать не нужно.

## Как устроен проект

Проект разделён на три части, как требует задание.

```
ProjectManagement.sln
├── src/ProjectManagement.DataAccess/     # работа с базой
├── src/ProjectManagement.Application/    # логика
├── src/ProjectManagement.Api/            # контроллеры (то, что видит клиент)
├── tests/ProjectManagement.Tests/        # тесты логики
└── client/                               # Vue-приложение
```

**DataAccess — доступ к данным.** Здесь сущности (`Project`, `Employee`, `ProjectEmployee`,
`WorkTask`, `ProjectDocument`), `ApplicationDbContext`, миграции и репозитории. Запросы к базе
собираются тут: фильтры и сортировка описаны классами `ProjectFilter` и `WorkTaskFilter`.

**Application — логика.** Сервисы `ProjectService`, `WorkTaskService`, `EmployeeService`,
`AccountService`, `AccessControlService`, `TokenService`. Здесь все проверки и права доступа.
Сервисы не знают про HTTP: вместо кодов ответа они возвращают объект `Result`, в котором
написано, получилось или нет, и почему (не найдено / нет прав / ошибка данных / конфликт).
Из-за этого логику удобно проверять тестами без запуска сайта.

**Api — представление.** Контроллеры только принимают запрос, зовут нужный сервис и
переводят `Result` в HTTP-код. Логики в них нет, к базе они не обращаются.
Перевод `Result` в ответ лежит в одном месте — `Controllers/ApiControllerBase.cs`.

Ссылки между проектами идут в одну сторону: Api → Application → DataAccess.

### Пара решений, которые стоит пояснить

- **Сотрудник — это же и пользователь.** Класс `Employee` наследуется от `IdentityUser`.
  Так не нужно держать две таблицы и следить, чтобы они совпадали: у сотрудника сразу есть
  имя, фамилия, отчество, email, пароль и роль.
- **Задача называется `WorkTask`, а не `Task`.** Иначе имя конфликтует с `System.Threading.Tasks.Task`
  и весь async-код пришлось бы писать с полными именами.
- **Проект в визарде сохраняется на 4-м шаге.** Документы привязываются к id проекта, поэтому
  к пятому шагу проект уже должен существовать в базе.
- **Файлы лежат на диске** в `wwwroot/uploads/{id проекта}`, а в базе хранится только описание
  файла. Имя на диске генерируется, чтобы файлы не перезаписывали друг друга.

## Что сделано по заданию

**Основное задание**

- Создание, просмотр, редактирование и удаление проектов, сотрудников и задач.
- Добавление и удаление сотрудников на проекте. Один сотрудник может быть на нескольких проектах,
  на одном проекте может быть несколько сотрудников (таблица связи `ProjectEmployee`).
- Фильтры для проектов: диапазон даты начала, диапазон приоритета, руководитель, поиск по тексту.
  Сортировка по названию, датам начала и окончания, приоритету. Список выдаётся страницами.
- Хранится всё, что перечислено в задании: название проекта, компания-заказчик,
  компания-исполнитель, ФИО и email сотрудника, руководитель проекта, даты начала и окончания,
  приоритет числом.

**Фронтенд**

- Визард из 5 шагов: данные проекта → компании → руководитель → исполнители → документы.
- На шагах 3 и 4 — выпадающий список сотрудников с поиском на сервере. Пока печатаешь, идёт
  AJAX-запрос `GET /api/employees?search=` (с задержкой 300 мс, чтобы не дёргать сервер на каждую букву).
- На шаге 5 — загрузка файлов через HTML5 с перетаскиванием (drag & drop).

**Дополнительное задание 1 — задачи.** Сущность `WorkTask` добавлена через миграцию.
Есть создание, просмотр, изменение и удаление; задача привязана к проекту; у задачи один
исполнитель, у сотрудника задач может быть много. Хранятся название, автор, исполнитель,
статус (ToDo / InProgress / Done), комментарий и приоритет. Есть фильтр по статусу, проекту,
исполнителю и поиск по названию, сортировка по названию, статусу и приоритету.

**Дополнительное задание 2 — права доступа.** Три роли: `Director` (руководитель),
`ProjectManager` (менеджер проекта), `Employee` (сотрудник).

| Что можно | Руководитель | Менеджер проекта | Сотрудник |
|---|---|---|---|
| Видит проекты | все | свои (где он руководитель) | те, куда его назначили |
| Назначать и убирать сотрудников с проекта | да | на своих проектах | нет |
| Управлять задачами, назначать исполнителя | да | на своих проектах | нет |
| Менять статус задачи | да | на своих проектах | у своих задач |
| Заводить новых сотрудников | да | нет | нет |
| Удалять проекты | да | нет | нет |

Все правила лежат в одном классе `AccessControlService` и покрыты тестами. На контроллерах
дополнительно стоит атрибут `[Authorize(Roles = ...)]` — это первая, грубая проверка,
а точную (например, «это мой проект или чужой») делает сервис.

## Обработка ошибок

Старался, чтобы пользователь не видел пустую 500-ю ошибку.

- Ошибки возвращаются в едином виде (`ProblemDetails`), в поле `message` — текст для показа.
  Коды: 400 — неверные данные, 403 — нет прав, 404 — не найдено, 409 — конфликт.
- Если указать несуществующего руководителя, исполнителя или проект, это проверяется до записи
  в базу. Иначе вместо понятного сообщения была бы ошибка внешнего ключа.
- Сотрудника, который руководит проектом или связан с задачами, удалить нельзя: вернётся 409
  с подсказкой, что сделать сначала.
- Если исключение всё-таки вылетело, его ловит `ExceptionHandlingMiddleware`: клиент получает
  нормальный ответ, а подробности пишутся в лог (в ответ они попадают только в режиме Development).
- Размер страницы и параметр `take` ограничены сверху, чтобы нельзя было запросить всю таблицу.
  Непонятное значение сортировки заменяется на значение по умолчанию.
- Для файлов есть список разрешённых расширений и лимит 25 МБ.
- Настройки JWT проверяются при старте: если в конфиге чего-то не хватает, приложение
  не запустится и сразу скажет об этом.

Ключ JWT в `appsettings.json` лежит открыто — это только для проверки задания.
В реальном проекте его нужно задавать через переменные окружения или user secrets.
